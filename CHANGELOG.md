## Unreleased

### `Deflate.flush(true)` emitted an invalid sync marker

`flush(true)` appends an empty non-final stored block so that everything
pushed so far is immediately decompressible. That marker was built from
`st.r`, which is a packed pair -- the bit offset within the pending partial
byte in bits 0-2, the byte's value in bits 3 and up -- but the whole packed
value was handed to `wfblk` as if it were a bit position, and the `+ 1` for
the BFINAL bit that every other `wfblk` call site accounts for was missing.
LEN and NLEN landed at the wrong offset, or past the end of the six byte
marker buffer where the writes were silently discarded, and inflaters
rejected the stream with `invalid stored block lengths`.

The failure is bit alignment dependent rather than size dependent: it fired
whenever the pending bit offset was exactly 6, or whenever the leftover
partial byte was non-zero. Small inputs happened to avoid both, which is why
this read as a large input problem. `flush(false)` was never affected.

### Streaming callback emission

Upstream 0.8.3 added support for sync flushes (`Z_SYNC_FLUSH` in zlib) and,
as a side effect, changed how often the streaming callbacks fire. Input that
0.8.2 delivered in a single `final: true` call could, under 0.8.3, arrive as
a data chunk with `final: false` followed by two empty chunks, the last of
which carried `final: true`. Code that captured "the chunk" instead of
concatenating chunks silently ended up with the trailing empty one.

- Streaming decompression (`Inflate`, `Gunzip`, `Unzlib`, `Decompress`) no
  longer emits zero length chunks unless the chunk is the final one. A small
  gzip member now yields the data chunk plus one empty `final: true` chunk
  rather than the 0.8.3 sequence of three calls.
- `FlateStreamHandler` and `AsyncFlateStreamHandler` now document the
  emission contract: a handler may be called any number of times, including
  zero, consumers must concatenate the chunks they receive rather than
  capturing one of them, and exactly one call has `final` set to `true`.

Collapsing back to 0.8.2's single call is deliberately not done. A gzip
stream cannot know its last member is the last one without buffering that
member's output, which would change the streaming memory profile. Consumers
that concatenate are correct under every version.
